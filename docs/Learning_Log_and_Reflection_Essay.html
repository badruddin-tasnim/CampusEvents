1. Technical Decisions

Developing CampusEvents for the CSE 3206 sessional required bridging the gap between theoretical software engineering principles and real-world system architecture. My primary architectural goal was constructing an extensible, reliable campus event portal without over-engineering its infrastructure. Choosing a component-driven React frontend coupled with Google Firebase provided immediate reactivity, but relying solely on cloud services introduced potential failure points during network disruptions or isolated offline lab environments. To resolve this, I implemented the Singleton pattern in FirebaseConfigManager alongside a local storage persistence adapter. This decoupled the presentation layer from the physical backend, allowing seamless execution whether connected to cloud Firestore or operating offline.

A second pivotal decision was enforcing object-oriented design patterns across business domains. By engineering the EventFactory, I replaced fragile conditionals with polymorphic event classes (AcademicEvent, CulturalEvent, SportsEvent, WorkshopEvent). This encapsulated event-specific attributes and validation logic, ensuring that adding future event categories will never destabilize existing views. Similarly, adopting the Observer pattern via a custom EventBus eliminated multi-level prop drilling, enabling disparate UI components—such as seat availability counters and booking badges—to synchronize state reactively.

2. Technical Challenges & Resolutions

The most demanding engineering hurdles arose at the intersections of testing, state management, and version control. Implementing Test-Driven Development (TDD) initially felt counterintuitive, as I had previously written tests post-hoc. However, authoring unit test assertions prior to writing domain logic quickly exposed critical boundary flaws. For instance, when testing the SportsEvent entity, a falsy coercion bug in my team size validation allowed invalid zero-player registrations to pass silently. TDD caught this defect before any frontend interface was connected.

Another significant challenge involved decoupling test suites from cloud infrastructure. Automated tests initially attempted real HTTP connections to Firebase Firestore, causing intermittent failures. I resolved this by authoring isolated module mocks with Vitest (vi.mock('firebase/firestore')) to simulate database transactions deterministically.

Finally, simulating and resolving a Git merge conflict between concurrent feature branches provided a profound lesson. Resolving the conflict required analyzing divergent validation logic on both branches, synthesizing them into a unified length check, and re-verifying automated test suites prior to committing. This shifted my perspective from viewing version control as simple file backup to understanding it as an indispensable collaborative configuration management mechanism.

3. Evaluation of Learning Resources

My self-directed learning journey relied on diverse technical resources, each offering distinct trade-offs. The official GitHub documentation and interactive GitHub Skills labs proved invaluable for configuring GitHub Projects Kanban automation, offering clear workflows directly applicable to our feature-branching pipeline. Refactoring.Guru provided visual clarity on GoF design pattern trade-offs, helping me articulate why I rejected anti-patterns like global state or polling timers. The Vitest documentation offered concise guides on modern ESM testing, though constructing asynchronous Firestore mocks required additional independent exploration. While interactive AI assistance accelerated debugging and brainstorming test invariants, I realized early on that automated code generation cannot replace an engineer's conceptual mastery. Every architectural decision and test assertion demanded my active comprehension to ensure architectural rigor and software reliability.

4. Plan for the Next Skill to Learn

Reflecting on the lessons gleaned from CampusEvents, the clear next frontier in my software engineering development is mastering Continuous Integration and Continuous Deployment (CI/CD) pipelines using GitHub Actions, integrated with automated End-to-End (E2E) testing via Playwright. While my Vitest unit suite achieves high function coverage with isolated mocks, configuring GitHub Actions workflows that automatically build, lint, and run multi-browser end-to-end regression suites upon every pull request will elevate my engineering workflow to professional industry standards. Mastering containerized deployments with Docker and automated cloud delivery constitutes my immediate technical roadmap for the upcoming academic semester.
