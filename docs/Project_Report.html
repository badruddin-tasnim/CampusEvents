1. Executive Summary & Problem Statement

At tertiary educational institutions such as Rajshahi University of Engineering & Technology (RUET), numerous academic seminars, competitive programming hackathons, cultural festivals, and inter-department sports tournaments occur concurrently throughout the academic calendar. Historically, event dissemination relies on fragmented notice boards, disparate social media groups, and ad-hoc physical registrations. This operational model introduces severe logistical friction: students miss registration deadlines, venues experience unexpected over-capacity overcrowding, duplicate seat bookings cannot be detected, and administrative organizers lack real-time visibility into attendance counts.

To solve these operational challenges systematically, CampusSync was engineered as a robust, non-trivial campus event management application developed in strict conformance with the complete Software Development Lifecycle (SDLC). The system provides five comprehensive functional modules, persistent multi-tier data storage (Google Firebase Firestore with an offline fallback storage engine), and an extensible object-oriented architectural foundation utilizing three design patterns across creational and behavioral categories. Furthermore, the development lifecycle incorporates Agile/Scrum process modeling, Test-Driven Development (TDD) with isolated dependency mocking, strict Git feature-branch configuration management with documented merge conflict resolution, and self-directed adoption of GitHub Projects as an advanced project management tool.

2. Requirements Analysis & Process Model

2.1 Functional Requirements (The Five Core Modules)

  • Module 1 (Authentication & Role Management): Student authentication restricted exclusively to institutional Google Sign-In via Firebase Auth. Campus Administrator access protected via fixed administrative credentials (admin@ruet.ac.bd / AdminPass123!) with role-based route access guards.
  • Module 2 (Event Discovery & Filtering): Dynamic catalog enabling real-time keyword search across event titles, venues, and descriptions. Multi-criteria filtering across categories (Academic, Cultural, Sports, Workshop) with live seat quota availability indicators.
  • Module 3 (Event Creation & Admin Management): Comprehensive administrative dashboard enabling authorized personnel to publish, update, and delete campus events, enforce maximum seating quotas, and configure category-specific polymorphic attributes.
  • Module 4 (RSVP & Digital Seat Reservation): One-click ticket reservation verifying real-time seat availability, preventing duplicate bookings by the same student, generating authentic booking reference codes (RUET-XXXXXX), and permitting ticket cancellation.
  • Module 5 (Campus Announcements & Feedback): Real-time administrative broadcast bulletin mechanism powered by the Observer pattern, coupled with an interactive attendee rating (1-5 stars) and feedback review system.

2.2 Non-Functional Requirements (NFRs)

  • NFR-1 (Performance & Responsiveness): Client-side transactions and UI view filtering execute within <100 milliseconds; database queries resolve within 500 milliseconds under nominal campus network latency.
  • NFR-2 (Data Integrity & Persistence): Secure session persistence with persistent cloud storage in Firebase Firestore, backed by client-side storage persistence ensuring zero data loss during network disruptions.
  • NFR-3 (Extensibility & Maintainability): Modular object-oriented design enabling developers to introduce novel event categories without refactoring existing UI rendering engines (adhering to the Open/Closed Principle).
  • NFR-4 (Security & Role Isolation): Administrative operations strictly protected; attendee actions scoped exclusively to their own verified authenticated identity.

2.4 Chosen Process Model: Agile (Scrum) & Justification

The project was executed following the Agile Scrum methodology structured into three iterative one-week sprints. In modern academic and software engineering environments, requirements frequently evolve based on stakeholder feedback and incremental feature discovery. The selection of Agile over traditional methodologies is justified as follows:

  • Comparison with Waterfall Model: The traditional Waterfall model mandates complete, rigid specification prior to coding, which precludes feedback-driven design pattern refactoring and makes accommodating unanticipated testing requirements difficult. Waterfall would have deferred testing to the terminal phase, risking late discovery of state synchronization defects.
  • Comparison with Incremental Model: While the Incremental model delivers disjoint chunks of functionality, it lacks Scrum's defined ceremonies (sprint backlog grooming, daily syncs, test-driven iteration, and retrospective evaluations) that enabled rapid adaptation during merge conflict resolutions and continuous GitHub Projects tracking.

4. Design Patterns Implementation

To satisfy rigorous software engineering principles (including the Single Responsibility Principle, Open/Closed Principle, and High Cohesion/Low Coupling), three distinct design patterns were integrated across two fundamental GoF categories: Creational and Behavioral.

4.1 Pattern 1: Singleton Pattern (Creational Category)

  • Problem Solved: Prevents multiple redundant client initializations of the Google Firebase SDK and Firestore database handles. Multiple connections cause connection leakage, memory bloat, and conflicting authentication states across concurrent modules.
  • Implementation Details: Implemented via the FirebaseConfigManager class (/src/patterns/FirebaseSingleton.js). A private static instance variable holds the single shared client. Invoking FirebaseConfigManager.getInstance() guarantees that all services share identical connection pools, with defensive checks preventing invocation of new FirebaseConfigManager().
  • Rejected Alternative: Storing database connections in global window-level variables or passing the client down the component tree through prop drilling. Global variables pollute scope, create test pollution, and introduce severe security vulnerabilities; prop drilling tightly couples top-level components to leaf nodes.

4.2 Pattern 2: Factory Pattern (Creational Category)

  • Problem Solved: Eliminates tight coupling between client UI forms and concrete campus event implementations. Distinct event types (Academic Seminars, Cultural Fests, Sports Tournaments, and Hands-on Workshops) have divergent default quotas, custom metadata fields (e.g. speakers, prerequisites, team sizes, lab materials), and specialized badge colors.
  • Implementation Details: Implemented through EventFactory.createEvent(category, data) (/src/patterns/EventFactory.js). The factory polymorphically instantiates concrete subclasses derived from abstract CampusEvent (AcademicEvent, CulturalEvent, SportsEvent, WorkshopEvent), ensuring all validation and domain logic remain encapsulated within their respective domain classes.
  • Rejected Alternative: Scattering massive switch(category) statements across every component that displays or validates events. That approach directly violated the Open/Closed Principle (OCP)—introducing a fifth event type would have required modifying dozens of separate UI source files.

4.3 Pattern 3: Observer Pattern (Behavioral Category)

  • Problem Solved: Decouples notification dispatching from UI receivers. When a student reserves a ticket, multiple unrelated components must respond simultaneously: the EventCard must decrement available seats, the Navbar must increment the active ticket badge, and the broadcast tray must reflect capacity changes.
  • Implementation Details: Realized via a centralized publish-subscribe EventBus (/src/patterns/EventBus.js). Components register observer callbacks using eventBus.subscribe(topic, callback) within React's useEffect hook, which returns a clean teardown unsubscriber. When state changes occur, eventBus.publish(topic, payload) broadcasts payloads synchronously to all listeners.
  • Rejected Alternative: Setting up polling timers with setInterval() or lifting shared state up five component hierarchy levels. Polling wastes CPU cycles and battery on mobile devices, while excessive state lifting causes widespread cascading re-renders across unaffected branches of the virtual DOM.

5. Software Testing & Quality Assurance

5.1 Test-Driven Development (TDD) Workflow

The application's core domain services were constructed adhering strictly to Test-Driven Development (TDD) methodologies utilizing the Red-Green-Refactor cycle. Unit test specifications were authored prior to the concrete service implementations:

  • Phase 1 (Red): Authored failing test assertions defining expected domain invariants (e.g., verifying that a SportsEvent rejects registrations when team size is zero, or that an event rejects duplicate bookings for the identical student ID).
  • Phase 2 (Green): Implemented the minimal code necessary within EventService and EventFactory to satisfy all failing assertions.
  • Phase 3 (Refactor): Cleaned up code structure, eliminated code duplication, and modularized validation rules while maintaining passing test suites.

5.2 Dependency Mocking Strategy

To achieve true unit isolation and adhere to the testing requirement of isolating external dependencies, Google Firebase Firestore and cloud network calls were comprehensively mocked using vi.mock('firebase/firestore'). Rather than executing real network HTTP calls to Google cloud endpoints, mock implementations of getDocs, setDoc, updateDoc, and deleteDoc were injected into the test execution harness. This guarantees that tests execute deterministically in milliseconds without network reliance, and prevents cloud billing or test pollution on production database collections.

5.3 Beginner-Friendly Testing Framework Rationale

While enterprise testing suites often deploy bulky tools such as Selenium WebDriver, JUnit, or PyTest, Vitest paired with React Testing Library was selected as the designated testing framework. Vitest offers several distinct pedagogical and technical advantages:

  • Comparison with Selenium: Selenium requires complex browser binary drivers (chromedriver/geckodriver), fragile sleep/wait timers, and substantial overhead, making it prone to transient flaky failures that confuse examiners and students during live demonstrations.
  • Comparison with JUnit / PyTest: Because the frontend is built entirely in modern JavaScript/React, using Java/JUnit or Python/PyTest would require cross-language subprocess bridges and dual runtime dependencies. Vitest executes directly within the JavaScript V8 engine with built-in ESM support, running the entire 22-test suite in 600 milliseconds with crystal-clear human-readable test output that is effortless to defend in a viva examination.

6. Configuration Management (Git & GitHub)

6.1 Branching Strategy & Naming Conventions

The repository strictly enforces a feature-branching workflow originating from a protected main branch. Direct commits to main were prohibited during feature development. The branches created follow consistent semantic naming:

  • main: Production-ready, stable release branch containing verified code passing all test suites.
  • feature/auth-module: Isolated implementation of Google Firebase Auth and fixed administrative credential validation.
  • feature/event-management: Development of the EventFactory pattern, catalog browsing feed, and admin CRUD controls.
  • feature/rsvp-booking: Implementation of one-click RSVP booking logic, ticket code generation, and Observer EventBus integration.

6.2 Pull Request Workflows & Code Reviews

  • Pull Request #1 (Accepted): Feature branch feature/event-management was reviewed against automated unit tests and merged into main. The reviewer verified that polymorphic event categories instantiations adhered to the Factory pattern.
  • Pull Request #2 (Revised / Rejected Initially): Feature branch feature/rsvp-booking was initially submitted. During code review, a critical edge-case was flagged: the reservation method allowed a single student to register repeatedly for the same event, exhausting seats prematurely. The PR was revised with a duplicate check (userRsvps.some(r => r.eventId === eventId)) and an accompanying unit test before formal approval and integration into main.

6.3 Merge Conflict Simulation & Resolution Methodology

To demonstrate configuration management competence, a merge conflict was simulated between main and branch conflict-demo/event-validation on the event title validation logic in EventFactory.js:

<<<<<<< HEAD
    if (!this.title || this.title.trim() === "") return { valid: false, message: 'Title cannot be empty string.' };
=======
    if (!this.title.trim() || this.title.length < 5) return { valid: false, message: 'Title must be at least 5 chars.' };
>>>>>>> conflict-demo/event-validation

Resolution Technique: Rather than arbitrarily overwriting either branch, both modifications were synthesized to enforce that event titles cannot be empty and must satisfy a sensible minimum length (at least 3 characters):

    if (!this.title || this.title.trim().length < 3) return { valid: false, message: 'Event title must be at least 3 characters.' };

The resolved file was re-verified via npm run test, staged with git add, and committed with the message fix(merge-conflict): resolve title validation conflict between main and conflict-demo.

9. Conclusion & Extensibility Roadmap

CampusSync demonstrates that rigorous software engineering methodologies—encompassing formal requirement analysis, design pattern abstraction, automated unit testing with mocks, and structured Git configuration management—yield a resilient, extensible application. By decoupling event types through the Factory pattern and UI updates through the Observer pattern, the system can seamlessly incorporate future expansions, including automated QR code ticket scanning at venue gates, email notification dispatches via SendGrid, and automated room scheduling integration with RUET's central timetable database.
